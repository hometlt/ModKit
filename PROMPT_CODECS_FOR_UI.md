# Задача для агента Сол — довести расширения и кодеки MK3 до работы с UI-компонентами

Ты продолжаешь работу над modkitX3 после срезов UK-1 (UI kit) и reference codecs.

## Контекст и владельческое решение

1. **UI-слой готов и зелёный.** В `packages/ui` есть 25 экспортов, 187 токенов, 175
   зарегистрированных частей, единый поставляемый лист `styles/modkit-ui.css`, четыре темы
   (`modkit-dark`, `modkit-light`, `modkit-high-contrast`, `vscode-adapter`).
2. **Твои reference codecs приземлились.** 12 кодеков, 11 стандартных data-source контрактов,
   16 viewer-манифестов.
3. **Стороны пока не сходятся полностью.** Компоненты умеют больше, чем кодеки отдают, и один
   дефект платформы блокирует вообще любой `codec.open()` в браузерном хосте.
4. На этом этапе **не переписывай UI-компоненты**. Их контракты — вход для тебя.

Проверить всё вживую можно так:

```bash
pnpm build && node examples/modkit-ui-gallery/scripts/build.mjs --serve
```

`http://localhost:8730/` — строгая продакшн-политика, `?csp=eval` — с `'unsafe-eval'`.
Разница между этими двумя загрузками и есть дефект P0-1.

## Главная цель

Сделать так, чтобы субъект, открытый любым MK3-кодеком, полностью питал уже существующие
UI-компоненты, **без ослабления продакшн-политики CSP и без знания форматов внутри UI**.

## Фаза A — read-only аудит

До изменений выясни и зафиксируй:

1. Какие из 11 стандартных контрактов реально публикует каждый из 12 кодеков.
2. Какие кодеки заполняют `descriptor.metadata` группами, а какие оставляют пустым.
   (`extensions/common/images/src/formats/png/codec.js:303` заполняет — проверь остальные.)
3. Какие кодеки заполняют `parameters` у объявленных traits.
   `PropertiesTable` рендерит именно их: `packages/ui/src/metadata/index.ts`.
4. Какие операции кодеки объявляют в дескрипторе — их рисует `OperationToolbar`.
5. Заполняет ли кто-нибудь `DetectionEvidence`; `DetectionEvidencePanel` из каталога компонентов
   на них рассчитан (доc 30 §5.1.3 требует персистентности, а не однократного вывода).
6. Что именно ломается под продакшн-CSP: воспроизведи P0-1 ниже.

Не начинай правки, пока аудит не записан.

## P0-1 — ajv ломает любой `codec.open()` в браузерном хосте

**Это блокирует всё остальное.**

Доказано измерением, не рассуждением:

| Среда                      | Результат                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Node, без CSP              | `codec.open()` для JSON проходит, три data source отдаются                                                                       |
| Браузер, продакшн-политика | `ModkitError: subject descriptor assembly failed validation` для всех 8 форматов text-data, плюс 9 нарушений `script-src — eval` |
| Браузер, `?csp=eval`       | всё работает                                                                                                                     |

Причина: `packages/sdk/src/manifest/validate.ts:43` создаёт `new Ajv(...)`, ajv компилирует
JSON Schema через `new Function`, а `script-src 'self'` без `unsafe-eval` это запрещает. Сборка
дескриптора идёт через `validateWithSchema`, ошибка бросается из `packages/host/src/session.ts:168`.
В бандле галереи ровно один `new Function` — внутри ajv.

Существующий `browser-e2e` этого не ловил, хотя ставит ту же политику: его сценарии не доходят до
валидации дескриптора теми же путями.

**Требуется:** прекомпиляция схем (`ajv/standalone`) на этапе сборки, с эмитом валидаторов как
исходника и drift-гейтом — это ложится в уже существующий в репозитории паттерн
`schemas:emit` / `schemas:check` / `manifests:check` / `tokens:check`.

Ослабление CSP решением **не считается**: политика вьюера защищает недоверенные вьюеры
(BRIEF-13C §6, доc 24).

Гейт: галерея по адресу без `?csp=eval` показывает все восемь форматов text-data и ноль
нарушений CSP.

## P0-2 — нет контракта для графа связей

`createRelationGraph` уже существует и работает, но питается фикстурой. Ему нужен источник:

```ts
// packages/ui/src/graph/index.ts — то, что компонент реально потребляет
interface GraphNode {
  id: string
  label: string
  type: string
}
interface GraphEdge {
  from: string
  to: string
  role?: string
  dead?: boolean
}
interface GraphTypeBucket {
  id: string
  label: string
  count: number
  tone: number
}
```

Спроектируй `common.view/relation-graph-source@1` по образцу остальных: пагинация через
`Page<T>`/`PageRequest`, `AbortSignal` на длительных операциях, бюджеты, и **обязательно**
честный отчёт об усечении — компонент показывает `capped`, если набор урезан, и не должен
получать молча обрезанные данные.

Отдельно нужны:

- `dead: true` для ссылок, которые не разрешились, — компонент рисует их цветом ошибки;
- корзины типов со счётчиками по **всему** графу, а не по видимому срезу (иначе счётчики врут).

Кандидат-потребитель: ZIP/архивы (граф вложенности), glTF (граф сцены), text-data (граф ссылок
внутри документа). Достаточно одного реального, но выбери его осознанно.

## P0-3 — нет источника для карточек субъектов

`createSubjectCard` собирает карточку из списка секций (`CardSection`): header, fields, links,
grid, cards, text, custom. Сейчас список приходит из фикстуры.

Ключевой инвариант, который нельзя нарушить: **юнит не владеет ни одним файлом**, его карточка
собирается из данных, разбросанных по многим. Файл — тоже субъект. Значит источник карточки не
может быть «прочитать этот файл».

Нужен контракт вида `common.view/subject-facts-source@1`, отдающий:

- идентичность и ссылки на происхождение (`Unit/Aquila`, `CUnit`, `UnitData.xml:315`);
- сгруппированные поля с провенансом каждого значения;
- связанные субъекты по ролям;
- необязательный превью-ресурс.

**Запрещено** (доc 06 §1, решение Q84): класть в дескриптор идентификаторы вьюеров, выбранные
фабрики или presentation plan. Карточка — проекция, а не состояние субъекта.

Композиция секций остаётся за хостом: он превращает факты в `CardSection[]`. Кодек фактов не
верстает.

## P1 — заполнить то, что компоненты уже рисуют

| Компонент                | Что читает                                                 | Что нужно от кодеков                                                           |
| ------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `MetadataPanel`          | `descriptor.metadata` (`MetadataGroup[]`)                  | группы у **всех** 12 кодеков, не только PNG                                    |
| `PropertiesTable`        | `descriptor.traits[].parameters`, `identity`, `operations` | осмысленные параметры traits вместо пустых объектов                            |
| `OperationToolbar`       | `descriptor.operations`                                    | объявлять реально поддержанные операции с корректным `state` и `mutatesSource` |
| `DiagnosticsPanel`       | `descriptor.diagnostics`                                   | structured diagnostics с `range`, когда парсер их может дать                   |
| `TransportBar`           | `TransportSnapshot.controls`                               | идентификаторы операций play/seek/rate/track — без них панель падает           |
| `DetectionEvidencePanel` | `DetectionEvidence[]`                                      | персистентные свидетельства обнаружения (доc 30 §5.1.3)                        |

`TransportSnapshot.controls` — не теория: фикстура без него роняла стейдж с
`Cannot read properties of undefined (reading 'playPause')`.

## P1 — thumbnail-режим

`ViewerMode` включает `thumbnail` с **отдельным бюджетом** (доc 06 §4): миниатюра не имеет права
поднимать тяжёлый runtime. Кодеки должны уметь отдавать дешёвое превью через `openIntent:
'thumbnail'`, не декодируя полный ресурс. Для `raster-image-source` это уже почти есть
(`decodedAccess`), для остальных — продумай.

## P2 — `browser-e2e` жёстко прописывает пути

`packages/ui/test/browser-e2e.test.ts` импортирует
`extensions/common/text-data/src/formats/<fmt>/codec.js` буквально. Во время разделения text-data
на семейства тест сломался с 16 неразрешёнными импортами.

Галерея тот же переезд пережила, потому что резолвит entrypoint'ы **из contribution-манифестов**
(`examples/modkit-ui-gallery/scripts/build.mjs`). Переведи e2e на тот же способ: манифест —
авторитет для entrypoint, а не путь в коде.

## Инварианты

- UI не знает форматов. Любая правка, добавляющая имя формата в `packages/ui`, — ошибка.
- Дескриптор не содержит идентификаторов вьюеров (доc 06 §1, Q84).
- Порядок регистрации не является authority: перестановка не меняет ни выбор, ни байты lock.
- Entry points загружаются лениво, после resolution и проверки разрешений; denied activation
  не импортирует provider.
- Продакшн-политика CSP не ослабляется. `VIEWER_CSP` уже содержит `media-src 'self' blob:` —
  это добавлено потому, что аудио- и видео-стейджи отдают blob платформенному плееру; не убирай.
- Каждый перенесённый алгоритм или фикстура — строкой в `PORTED.md` с исходным путём и commit.
- Новые контракты классифицируются **по одному**, с указанием вида: data source, service
  provider, operation, presentation preference или host facility. Пакетного утверждения нет.

## Acceptance

1. `pnpm check` зелёный: build, bench-гейт, lint, format, тесты, schemas, manifests, tokens, legacy.
2. Галерея **без** `?csp=eval` показывает все восемь форматов text-data и ноль нарушений CSP.
3. Каждый из 12 кодеков даёт непустой `MetadataPanel` и осмысленный `PropertiesTable`.
4. `RelationGraph` питается настоящим источником хотя бы для одного расширения, счётчики типов
   считаются по полному графу, усечение сообщается.
5. `SubjectCard` собирается из фактов настоящего субъекта, при этом дескриптор остаётся без
   идентификаторов вьюеров.
6. Thumbnail-режим не поднимает полный декодер — доказано измерением, а не комментарием.
7. `browser-e2e` резолвит entrypoint'ы из манифестов и переживает переименование каталога.
8. Ни один новый `--mk-*` не появился без регистрации в реестре токенов; `tokens:check` зелёный.
9. Ни одна новая часть DOM не появилась без регистрации в `parts.ts`.

## Stop conditions

Остановись и запроси решение владельца, если:

- прекомпиляция ajv требует изменить bootstrap closure;
- для графа или карточки нет способа выразить контракт без знания формата в UI;
- требуется положить в дескриптор что-либо про вьюеры;
- thumbnail невозможно отдать без полного декодирования — тогда это отдельный provider-слой;
- любая задача требует ослабить `VIEWER_CSP`.

## Формат ответа

Начни с вердикта: `READY FOR IMPLEMENTATION` / `READY WITH NON-BLOCKING GAPS` /
`BLOCKED BY OWNER DECISION`. Затем: аудит фазы A, точное дерево изменяемых файлов, классификация
каждого нового контракта, тестовая матрица, последовательность коммитов, вопросы владельцу.

**Не начинай P0-2 и P0-3 до закрытия P0-1**: пока валидация дескриптора падает под продакшн-CSP,
проверить остальное в браузерном хосте невозможно.
