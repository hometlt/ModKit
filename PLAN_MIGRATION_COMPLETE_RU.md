# Программа полного перехода с modkitx на modkitX3

**Цель владельца:** довести X3 до состояния, в котором старым modkit можно перестать пользоваться.

Этот документ отвечает на три вопроса: **что именно недостаёт**, **в каком порядке это делать**, и
**по какому признаку переход считается состоявшимся**. Всё измерено на деревьях 2026-08-24, а не
оценено.

Блок 9 (`PLAN_SOL_BLOCK9_FINAL_2026-08-24.md`) остаётся в силе без изменений — он первый шаг этой
программы.

## 4. Артефакт, без которого программа неуправляема: реестр перехода

Нельзя планировать «весь недостающий функционал» по строкам кода. Строка — не функция.

**Шаг 0 программы: `docs/MIGRATION_REGISTER_RU.md`** — список **пользовательских возможностей**
старого modkit, каждая со статусом в X3.

Строка реестра:

| Возможность | Где в каноне | Статус в X3 | Чем доказано | Блок |
| ----------- | ------------ | ----------- | ------------ | ---- |

Статусы ровно четыре:

- `есть` — работает, есть доказательство (тест или живой прогон);
- `частично` — работает мельче канона, названо **чем именно** мельче;
- `нет` — не перенесено;
- `не переносим` — сознательное решение владельца с причиной.

Источники для составления: `pnpm parity` (машинная часть), меню и команды плагина VS Code,
`docs/MK3/*` канона, реестр контрибушенов, и — обязательно — **прогон владельца по своим типичным
задачам**.

Реестр — единственное место, где живёт ответ «что осталось». Он обновляется в конце каждого блока;
блок без обновления реестра считается незакрытым.

Матрица различий, которую он и так строит, — половина этой работы.

### Блок 10 — инвентаризация VS Code + Relic

Два независимых потока в одном блоке:

1. **Разобрать плагин канона по функциям, а не по строкам.** Результат — список возможностей с

   Без неё пункт C программы не имеет объёма, и любые сроки будут выдуманными.
2. **Relic** (`relic-essence` 7 + `relic-models` 2 = 9 contributions) — продолжает модельную
   вертикаль, `mk2/` уходит с 25 до 23.

### Блоки 11–13 — глубина форматов по списку паритета

Категория A, порядок — по строкам `X3 беднее` из паритетного гейта, с приоритетом владельца:
**SC2 и C&C впереди остальных игр**. Пакетами по 3–5 форматов, каждый пакет — коммит с зелёным
гейтом и обновлённой строкой паритета и реестра.

Ожидаемое распределение: `data-processing` и `models-processing` (27 706 строк вместе) — основная
часть; они же дают наибольший видимый эффект пользователю.

### Блоки 14–15 — трёхмерная отрисовка

1. Браузерный бэкенд до практической полноты — то, ради чего существует `webgl-core`.
2. `scene-core` **не переносится в общий рендер**: terrain/doodads/battle распределяются по игровым
   расширениям, иначе общий рендер выучивает конкретные игры и ломает границу, которую охраняет
   `reference-codecs-packed.test.ts`.
3. Three.js остаётся опциональным вкладом и не входит ни в одну сборку по умолчанию.

### Блок 16+ — VS Code по результатам инвентаризации

Объём назначается блоком 10. Если инвентаризация покажет, что большая часть 92 590 строк —

## 6. Критерий: когда переход состоялся

Переход считается состоявшимся, когда одновременно:

1. **Реестр перехода не содержит строк `нет`**, а каждая `частично` либо закрыта, либо переведена
   владельцем в `не переносим` с причиной.
2. **Паритетный гейт покрывает все contributions** и не содержит **необъяснённых** `X3 беднее`.
   Объяснённые допустимы — они и есть сознательные границы.
3. **`extensions/mk2/` пуст.**
4. **Живые прогоны на настоящих установках владельца** проходят без skip: SC2, C&C 3, и любые
   другие игры, которыми владелец реально пользуется.
5. **Все приложения дают одинаковый набор возможностей** — Electron, PWA, VS Code, CLI,
   встраиваемый компонент. Возможность, доступная в одном и недоступная в другом, попадает в
   реестр строкой.
6. **Владелец проработал неделю в X3, не открывая старый modkit.** Это единственная проверка,
   которую нельзя подделать гейтом, и она обязательна.

Пункт 6 — не формальность. Гейты меряют то, что мы догадались измерить; ежедневная работа находит
то, о чём мы не подумали.

## 7. Честная оценка

Остаётся перенести примерно **145 000 строк смысла** (A + B + D, при неизвестном пока C), плюс
расселение 25 семейств. Блоки 7 и 8 показали пропускную способность порядка 10–15 тысяч строк
результативной работы на блок.

Отсюда: **порядка 12–18 блоков** до критерия §6, при условии что инвентаризация VS Code не откроет
неожиданного объёма. Это оценка порядка величины, а не обещание срока; она уточняется после блока 10,
когда пункт C получит настоящий объём.

Сокращать этот путь можно ровно одним способом — **сознательно объявлять части «не переносим»**.
Каждое такое решение принимает владелец, и оно записывается в реестр.
