## 1. Правила работы

1. **Гейт запускается фазами, не одной командой.** Сторожевой таймер снимает агента после 600 с
   молчания. Порядок: `pnpm build` → `pnpm lint && pnpm format:check` →
   `pnpm exec tsc -p tsconfig.tooling.json` → `pnpm exec vitest run <свои каталоги>` → `pnpm test`
   → остальные `*:check` (включая `pnpm ports:check`). Между фазами пиши строку вывода.
2. **Ничего не запускай параллельно с гейтом в том же дереве.** `tsc -b` после `pnpm build`
   пересобирает `packages/*/dist` в многофайловый вид и разваливает бандлы — увидишь «still
   imports its own modules» и будешь чинить несуществующий регресс.
3. **Упавшее под нагрузкой перепроверяй в одиночку** прежде чем считать дефектом.
4. **`dist-app` и `scripts/bundle-hashes.json` собирает Root после слияния** — собери, проверь,
   потом `git checkout --` этих путей. В отчёте не пиши «не затрагивал», если файл изменён:
   проверь `git status` перед тем, как это утверждать.
5. **Новый субпуть в `exports`** требует записи в `PUBLISHED_ENTRIES` (`scripts/test/bundle.test.ts`).
6. **Маркер поверхности в тестах сборки — строка её собственного кода, не имя part.**
7. **Жёсткие переписи, ломающиеся при перестановке расширений:**
   `packages/testkit/test/text-data.test.ts`, `scripts/app-extension-sets.mjs`,
   `scripts/check-apps.mjs`, плюс `contributes:check` для VS Code. В этом блоке они сломаются
   гарантированно — планируй это, а не удивляйся.
8. **Запреты, проверяемые гейтами:** `capability` не может быть ключом объекта/схемы; format id не
   должен появляться в исходниках `core/sdk/vfs/host` **даже в комментарии**; никаких `!`,
   `as any`, `@ts-ignore`, управляющих символов; `VIEWER_CSP` не меняется.
9. **`../modkitx` — строго только для чтения.** Читай, переноси смысл, ничего там не меняй.
10. **Коммиты на своей ветке, без push**, сообщение заканчивается
    `Co-Authored-By: Claude Sol <noreply@anthropic.com>`.

### Стандарт доказательства

- **Electron** запускается здесь: `cd apps/electron && node scripts/build-app.mjs && node_modules/.bin/electron.CMD electron/main.cjs --open <папка> --selftest --enable-logging`. Гоняй на маленькой папке.
- **Браузер** запускается: образцы — `apps/web/test/{boot,embed,edit-panel}.test.ts`.
- **VS Code не запускается** — доказывай тестами и сборкой, и **пиши в отчёте, что осталось
  непроверенным живьём**.
- Файлы игр владельца **не кладутся в репозиторий**: путь через переменную окружения, отсутствие
  файлов даёт **видимый пропуск**, а не зелёный прогон.

## 2. Порядок в `extensions/` — правило, а не разовая уборка

Сегодня там пять групп, и они смешаны по смыслу: продуктовые расширения, инструментарий, образцы
контрактов и временная площадка переезда лежат рядом. Введи и примени **одно правило**:

| Группа        | Что туда попадает                                          | Сейчас                    |
| ------------- | ---------------------------------------------------------- | ------------------------- |
| `common/`     | универсальные форматы, не привязанные к вендору            | 15 — остаётся             |
| `<vendor>/`   | форматы конкретного вендора/движка (`blizzard/`, `ea/`, …) | 2 — растёт                |
| `codec-kit/`  | инструментарий авторов кодеков                             | 1 — остаётся              |
| `_reference/` | **эталонные реализации контрактов, не продукт**            | сейчас `reference/`       |
| ~~`mk2/`~~    | временная площадка                                         | 42 — **должна исчезнуть** |

### 2.1 Что такое `reference/` и почему это не мусор

Там две вещи, и обе — **эталонные реализации контрактов**, а не форматы:

- `counter-runtime` — эталон `common.runtime/provider@1`: доказывает, что контракт исполнения с
  бюджетами (время, тики, память) работает и что превышение возвращает структурный отказ;
- `software-renderer` — эталон `common.render/scene-3d@1`: принимает декодированные треугольники и
  возвращает RGBA8-кадр.

Их потребляют **только тесты** (`packages/host/test/{renderer,runtime}.test.ts`,
`packages/sdk/test/renderer-contract-types.ts`). Контракт без эталонной реализации — это
непроверенное обещание, поэтому удалять их нельзя. Но лежать вперемешку с продуктовыми
расширениями им не место.

**Действие:** переименовать `extensions/reference/` → `extensions/_reference/` (подчёркивание, как
у `_shared` раньше — «это не продукт»), и в `README.md` каждой написать одной строкой, эталоном
какого контракта она является и кто её потребляет. Обновить пути в трёх тестах.

**Важно для §4:** `software-renderer` — эталон ровно того контракта, который в 3D-вертикали будет
реализовываться по-настоящему. Это отправная точка, а не балласт.

### 2.2 Убрать лишнее

- **`packages/extensions-linked/` — удалить.** Пустой остаток завершённой миграции: нет
  `package.json`, `generated/` пуста, никто не ссылается. Механизм статической линковки жив и
  переехал в `src/linked.js` внутри каждого расширения — это правильнее, генератор больше не нужен.
  Перед удалением проверь ссылки в `pnpm-workspace.yaml`, `tsconfig.json`, `PUBLISHED_ENTRIES` и
  документации.
- Пройди `extensions/` на предмет других остатков: пустые каталоги, `node_modules` без пакета,
  README, описывающие несуществующий механизм. Каждый случай — в отчёт с причиной.

### 2.3 Расселение `mk2/` — сколько получится

42 семейства. Расселяй **по одному семейству за коммит**, в целевую группу (`common/` или
вендорскую), с обновлением манифестов, наборов расширений и переписей из правила §1.7.

Не обязательно закрыть все 42 в этом блоке. Обязательно: **семейства, затронутые приоритетом §3–§4,
переезжают полностью**, а для остальных в отчёте — список и оценка.

## 3. Приоритет: общие форматы и SC2

### 3.1 Общие форматы (`common/`)

Довести до состояния «формат отдаёт то, что объявляет» и расселить из `mk2/common-*` в `common/`.
Опирайся на паритетный гейт (§5) — он скажет, где мы беднее канона.

### 3.2 StarCraft 2

Вертикаль уже частично есть: CASC открывает настоящую установку, есть `blizzard/starcraft2-game` и
`blizzard/galaxy-language`, кодек `m3` лежит в `extensions/mk2/blizzard-models/src/m3/codec.js`.

Довести до конца:

1. **`m3` переезжает** из `mk2/blizzard-models` в `blizzard/` и углубляется до настоящей геометрии
   (см. §4 — это же вход в 3D-вертикаль);
2. **текстуры** (`dds`) отдают картинку;
3. **данные** (`sc2-data`, `sc2-strings`, `sc2-layout`) отдают дерево и таблицы;
4. цепочка **CASC → MPQ → m3/dds** проверена живьём на установке владельца, с указанием в отчёте,
   на каких файлах.

## 4. Приоритет: 3D-модели и отрисовка

Это самый большой отдельный кусок работы и самый заметный результат для пользователя.

### 4.1 Что есть сейчас

| Где                                       |            Строк | Что                                                  |
| ----------------------------------------- | ---------------: | ---------------------------------------------------- |
| `extensions/common/models`                |            1 966 | obj, gltf/glb, uvm — слой осмотра                    |
| `extensions/mk2/common-models`            |            4 020 | dae, ply, stl и др.                                  |
| `packages/ui/src/model`                   |              653 | вьювер сцены                                         |
| `extensions/_reference/software-renderer` |                — | эталон `common.render/scene-3d@1`                    |
| **канон `rendering-3d`**                  | **21 705** (src) | настоящие бэкенды: browser, headless-node, backends/ |

### 4.2 Что сделать

Порядок продиктован зависимостью: **сначала геометрия, потом её отрисовка.**

1. **Геометрия из кодеков.** Модельные кодеки должны отдавать `common.view/model-scene-source` с
   настоящими примитивами (позиции, индексы, нормали, UV), а не только дерево узлов. Начни с
   `glb/gltf` (эталонный, хорошо документирован) и `m3` (приоритет SC2). Помни: типизированные
   массивы через RPC уже ходят — это чинилось отдельно.
2. **Отрисовка как опциональное расширение.** По целевой таблице канона контракты сцен остаются в
   `sdk`, а бэкенды — опциональные вклады. Перенеси `headless`-бэкенд канона первым: он
   детерминированный и **проверяемый в тестах без экрана** (канон рендерит PNG-фикстуру — тот же
   приём даёт нам доказательство).
3. **Браузерный бэкенд** — после headless, когда контракт подтверждён детерминированным путём.
4. **`software-renderer` остаётся эталоном** контракта, а не заменяется: он и настоящий бэкенд
   должны удовлетворять одному контракту, и это проверяемо одним набором тестов.

### 4.3 Критерий готовности 3D-вертикали

- модель SC2 (`m3`) и модель общего формата (`glb`) отдают настоящую геометрию;
- headless-бэкенд рендерит их в PNG **в тесте**, без экрана;
- Electron показывает сцену живьём — доказано самопроверкой;
- эталонный и настоящий бэкенды проходят один контрактный тест.

## 5. Паритетный гейт — узкое место, делать рано

Инструмент, открывающий один и тот же файл **в обоих деревьях** и сравнивающий: дескриптор,
метаданные, объявленные против фактически отданных источников данных, операции.

- одна команда, таблица «формат → канон отдаёт → X3 отдаёт → разница»;
- классификация: `паритет` / `X3 беднее` / `X3 богаче` / `нет в X3`;
- файлы владельца — через переменную окружения, отсутствие = **видимый пропуск**;
- отчёт сохраняется, чтобы прогресс был сравним между прогонами.

Без него «без регрессий относительно modkitx» проверить нечем, а приоритеты §3–§4 выполняются
вслепую. **Строй его до массового углубления, а не после.**

## 6. Порядок работ

```
1. Уборка (§2.1 _reference, §2.2 удалить extensions-linked)   — маленький, первым
2. Паритетный гейт (§5)                                        — узкое место
3. Геометрия моделей: glb → m3 (§4.2 п.1)                      — вход в 3D
4. Headless-бэкенд отрисовки (§4.2 п.2)                        — доказуемо без экрана
5. SC2-вертикаль до конца (§3.2)                               — CASC → MPQ → m3/dds
6. Расселение mk2/ по затронутым семействам (§2.3)
7. Общие форматы по списку гейта (§3.1)
```

Разумный первый заход: **шаги 1–3**, отчёт. Не пытайся закрыть блок целиком.

## 7. Отчёт

1. **Что легло** — файлы и суть.
2. **Доказательство** — что проверено живьём (с реальными строками вывода), что тестами, что
   осталось непроверенным. Какие падения перепроверял в одиночку после нагрузки.
3. **Таблица паритета** — если гейт построен, приложи срез.
4. **Дефекты вне твоей зоны** — нумерованно, с `файл:строка`. Это самая ценная часть отчёта.
5. **Что не сделано и почему** — прямо. Список нерасселённых семейств с оценкой.
6. **Состояние `git status`** — перед утверждением «не затрагивал» проверь фактически.
