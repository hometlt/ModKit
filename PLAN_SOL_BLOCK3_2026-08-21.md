# Задание для Sol — блок 3: VFS, namespace-вход, чистка структуры

Ветка `spec/mk3-extension-reference`. Правила работы, стандарт доказательства и запреты — из
`PLAN_SOL_BLOCK2_2026-08-20.md` §1, действуют **без изменений**. Куда всё ведёт —
`docs/TARGET_STATE_RU.md`.

Первая волна блока 2 принята: `pnpm ports:check` → 181/19/162, полный гейт зелёный (проверено
независимо). Твой отказ портировать CASC был правильным, и разбор владельца после него нашёл
причину глубже, чем предполагалось. Этот блок — про неё и про наведение порядка в структуре.

---

## 1. Главная находка: VFS не перенесён

Ты уперся в то, что хост принимает только байтовый источник. Это верно, но это **симптом**.
Сравнение с соседним репозиторием:

|           | MK2 `packages/vfs`                                                                                                      | MK3 `packages/vfs`                  |
| --------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| файлов    | 34                                                                                                                      | 2                                   |
| строк     | тысячи                                                                                                                  | **103**                             |
| что умеет | mount, overlay, resolver, cache, провайдеры **file / browser-file / git / github / http / memory**, детекция провайдера | `RandomAccessSource`, память, стрим |

**Виртуальная файловая система в MK3 не перенесена.** Возможность «одинаково открывать файлы из
разных источников, включая архивы» — та, ради которой VFS существует, — отсутствует.

И три известных долга оказываются **одной работой**, а не тремя:

- CASC не открывается (install-root — это не байтовый источник);
- запись архива нельзя переоткрыть как самостоятельный субъект;
- открыть что-либо по URL/из git нельзя вообще.

---

## 2. Решения владельца (приняты, действуй по ним)

**2.1. VFS — минимум сейчас, провайдеры подключаются по отдельности.**
Не переносить MK2-VFS целиком. Сделать ядро + ровно то, что нужно для namespace-входа, а
провайдеры оформить **как независимо подключаемые модули**: git нужен редко, browser-file только в
браузере, http не всегда, монтирование архива — только если приложение с архивами работает. Плюс
должны быть возможны кастомные протоколы (API конкретного сайта, специфичное хранилище).

Это ровно тот же принцип, что уже действует для вьюверов: субпуть на поверхность, `sideEffects:
false`, и гейт, который ловит лишнее в бандле. VFS обязан ему подчиняться.

**2.2. `extensions/_shared` → `extensions/codec-kit`.**
Подчёркивание — не имя. Каталог остаётся **вне `packages/`**: приложениям импортировать
`@modkitx-x3/codec-kit` запрещено гейтом (`scripts/check-app-imports.mjs:58`), и визуальное
соседство с `core/sdk/host/ui`, которые импортировать можно, стирало бы эту границу.

**2.3. `packages/extensions-linked` — убрать вместе с генератором.**
Причина, проверенная в коде: генератор существует **только ради дайджестов**, а проверка дайджеста
в статической полосе — тавтология:

```js
verifyArtifactDigest: expected => expected === init.artifactDigest
```

Она сравнивает значение само с собой и не может провалиться. В шапке `packages/host/src/linked.ts`
прямо написано, что импорт и есть решение о доверии, — и тут же требуется дайджест, чтобы
удовлетворить форму `ExtensionInput`. Цена этой церемонии: 315 строк генератора и 5028 строк
сгенерированного кода.

**2.4. Кодеки дробятся по `<вендор>-<домен>`, а не по игре.**
Сейчас `blizzard-starcraft-2` — одно расширение на 12 контрибушенов (`galaxy`, `m3`, `sc2-map`,
`sc2-replay`, `sc2-bank`, …). Кому нужны только модели — тянет реплеи и триггеры. Расширение это
единица поставки и доверия, дробить его надо по домену.

## 3. Задачи

### Этап 1. VFS-ядро и провайдеры (платформа)

**1.1. Ядро `@modkitx-x3/vfs`.**
Путь, узел (файл/каталог), провайдер, резолвер, монтирование. Только то, что нужно, чтобы
«источник» перестал означать «байты одного файла». Никаких провайдеров внутри ядра.

**1.2. Провайдеры — отдельные субпути.**
`@modkitx-x3/vfs/providers/file` (Node), `…/memory`. Всё остальное — **позже и по потребности**:
`browser-file`, `http`, `git`, `github`, `archive-mount`. Требования к каждому:

- подключается импортом субпути и регистрируется явно, никакого автоподхвата;
- ядро не знает о провайдерах (иначе один импорт потянет все);
- у провайдера есть границы (сколько записей, сколько байт) и именованные отказы.

**1.3. Кастомный протокол — публичная возможность, а не лазейка.**
Контракт провайдера должен позволять внешнему разработчику написать свой (API сайта, специфичное
хранилище) и зарегистрировать его в приложении. Опиши это в `docs/GUIDE_DEVELOPER_RU.md`.

**1.4. Приёмка этапа 1 — гейтом минимальной сборки.**
Добавь случаи в `scripts/test/minimal-build.test.ts`: потребитель `vfs/providers/file` **не несёт**
ни git, ни http, ни browser-file. Маркеры — строки самих провайдеров, не имена типов (правило §1.6
блока 2).

### Этап 2. Namespace-вход поверх VFS

**2.1.** `OpenSubjectOptions.source` расширяется до `ArtifactSource`; каталог-как-субъект приходит
через VFS-провайдер, а не через отдельный самодельный источник.
**2.2.** Ограниченный namespace-probe: кодек называет файлы-маркеры, хост читает **только их**.
Обход всей игры на десятки гигабайт запрещён и должен отказывать по бюджету с причиной.
**2.3.** `codec-kit` учится `originKind: 'namespace'` (сейчас `single`/`bundle`, иначе
`throw ... requires a physical byte input`).
**2.4. Приёмка:** временный каталог-фикстура открывается через продуктовый путь, выход за `roots`
отказывается. **Без CASC** — платформа доказывается сама.

### Этап 3. CASC на настоящей установке

Только после этапа 2. Доказательство — `C:\Apps\StarCraft II`, тем же способом, что ты уже
применил (`skipIf`, env-override, реальные байты). Извлечение — стандартным `container.extract`.
Перечисление страничное и прерываемое.

**Немедленный эффект:** уже портированные `m3`, `dds`, `mpq` начинают открываться **изнутри**
хранилища, а не только из распакованных папок.

### Этап 4. Чистка структуры

**4.1. Убрать `packages/extensions-linked` и генератор.**
Вместо него — у каждого расширения свой маленький `linked` entry (JSON-импорты манифестов +
`import * as` модулей + `defineLinkedExtension`). Дайджест в статической полосе сделай
необязательным: он ничего не доказывает, и требовать его — значит держать генератор ради формы.

Одну вещь генератор делал хорошо: **он не мог забыть новый манифест.** Поэтому вместо него —
маленький гейт (~30 строк): каждый контрибушен расширения обязан быть упомянут в его `linked`
entry. Это замена 315 строк генератора и 5028 строк вывода на 15 строк на расширение плюс проверку.

Убери `linked:check` из цепочки сборки, `PUBLISHED_ENTRIES` и `pnpm-workspace.yaml` привести в
соответствие.

**4.2. `extensions/_shared` → `extensions/codec-kit`.**
Переименование каталога; имя пакета `@modkitx-x3/codec-kit` не меняется. Проверь
`pnpm-workspace.yaml`, гейты путей и `scripts/check-app-imports.mjs`.

**4.3. Дробление по `<вендор>-<домен>`.**
Начни с того, что уже портировано, чтобы дробление сразу проверялось: `blizzard-mpq`,
`blizzard-casc` (после этапа 3), `blizzard-models` (m3, m3a), `blizzard-starcraft2` — только
SC2-специфичное (`sc2-map`, `sc2-mod`, `sc2-replay`, `galaxy`, `sc2-data`, …).
Наборы приложений (`mk2-extended`) должны позволять подключать расширения **поштучно**, иначе
дробление не даст эффекта на уровне приложения.

### Этап 5. Аудит регрессий против MK2

В соседнем репозитории **34 пакета**: `archives-processing`, `maps-processing`,
`replays-processing`, `rendering-3d`, `lsp`, `localization-processing`, `saves-processing`,
`mods-processing`, `scripts-processing`, `semantic`, `knowledge`, `world`, `entity-cards` и др.

Сделай таблицу: **пакет MK2 → что он давал → где это в MK3 → есть / нет / не нужно**. Не «оценю по
названиям» — открой и посмотри. Результат — `docs/AUDIT_MK2_PARITY_RU.md`.

VFS уже найден как непереносённый; таких может быть больше. Это не работа по исправлению — это
**инвентаризация**, чтобы «регрессий нет» перестало быть предположением.

## 4. Порядок

1. Этап 4.2 (переименование `_shared`) — дёшево, убирает раздражитель.
2. Этап 1 — VFS-ядро и файловый провайдер, с гейтом минимальной сборки.
3. Этап 2 — namespace-вход.
4. Отчёт. **Останавливайся здесь**, если платформа заняла больше ожидаемого.
5. Дальше: этап 3 (CASC), 4.1 (удаление генератора), 4.3 (дробление), 5 (аудит).

## 5. Отчёт

Формат прежний, плюс:

- **что именно попало в VFS-ядро и почему ровно столько** — соблазн перенести весь MK2-VFS велик,
  а решение владельца обратное: минимум и рост по потребности;
- **числа гейта минимальной сборки** для провайдеров: что не приехало и чем это доказано;
- **если удаление генератора оказалось дороже, чем 15 строк на расширение** — скажи прямо, это
  решение принято на основании подсчёта, и подсчёт может оказаться неверным;
- таблица аудита MK2, если дошёл до этапа 5.
